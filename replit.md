# Silent Witness

## Overview

Silent Witness is a privacy-first evidence fingerprinting tool. It allows users to create cryptographic fingerprints (SHA-256 hashes) for files, videos, audio, documents, and written testimony — entirely in the browser, without ever uploading original files to any server.

Silent Witness does NOT publish original evidence files. It only creates and stores fingerprints, safe descriptors, and public metadata. The original file must stay on the user's device.

## What Silent Witness Does

- Creates SHA-256 fingerprints of files and testimony locally in the browser
- Submits only the fingerprint + safe metadata to the public registry
- Runs automatic policy checks on submission; records that pass appear **immediately** in the registry — no manual review step
- Timestamps fingerprints with a server-generated UTC time (the client cannot set or override this)
- Provides a public registry for later comparison with original evidence
- Supports retraction: the holder can remove their public record using a token saved in their proof package

## What Silent Witness Does NOT Do

- Does not upload or store original evidence files
- Does not prove that a crime occurred or that an event happened
- Does not identify a perpetrator
- Does not guarantee legal admissibility
- Does not recover deleted files (a hash cannot reconstruct the original)
- Does not have a manual reviewer/admin dashboard (removed in v0.1)
- Does not include Telegram integration (removed in v0.1)
- Does not include blockchain anchoring (future work)

## Timestamp Model

- `createdAtLocal` — generated by the user's browser at fingerprint creation time. Comes from the device clock. **Not independently verified.** Displayed with a warning.
- `serverReceivedAtUtc` — set exclusively by the server when the POST /api/records request is received. The frontend cannot set or override this field. Proves the registry received the fingerprint by that time.

## Exact Hash Limitations

Exact SHA-256 matching only works if the later file is **byte-for-byte identical** to the original.

Files sent through WhatsApp, Telegram, Facebook, YouTube, or other platforms are often compressed or re-encoded, changing their SHA-256. If no exact match is found, it does not mean the file is fake — it may have been compressed or exported by another platform.

Exact verification requires the original file or an exact safe copy, not a platform-downloaded version.

## Automatic Publication Workflow

Records do not go through manual review. The workflow is:

1. User creates fingerprint locally in browser (no upload)
2. User submits fingerprint → server runs automatic policy checks
3. If passes: `publication_status = accepted_public` — immediately visible in registry
4. If fails safety/quality: HTTP 400 with `status: rejected_by_policy` and a reason message
5. Holder can retract using their retraction token → `publication_status = retracted_by_holder`

## Publication Status Vocabulary

| Status | Meaning |
|---|---|
| `accepted_public` | Passed all policy checks. Visible in public registry. |
| `rejected_by_policy` | Failed safety or quality checks. Never shown publicly. |
| `retracted_by_holder` | Holder used retraction token to remove. Not shown publicly. |
| `exact_match_published` | A later file was verified as byte-for-byte identical. |

## Policy Checks (server-side, automatic)

Before a record is accepted, the server checks:
- **Quality**: must be level A, B, or C. Quality D (empty/minimal/spam) is rejected with 400.
- **Location fields**: country/region/city must not contain phone numbers, GPS coordinates, URLs, email addresses, street addresses, vehicle plates, or violent language.
- **Honeypot**: bot submissions silently discarded.
- **Duplicate**: duplicate package hash returns 409.
- **Rate limit**: 10 submissions per IP per hour.

## Quality Level Rules

- A = event type + evidence type + safe descriptor populated
- B = evidence type + descriptor but event or evidence type withheld
- C = minimal — event/evidence type only (no descriptor)
- D = both event type and evidence type withheld with no descriptor → rejected

## Retraction Token

When a user creates a proof package:
- A UUID retraction token is generated locally in the browser
- The SHA-256 of `"sw-retract:" + token` is sent to the server (only the hash is stored)
- The raw token is included in the downloaded proof package only
- To retract: POST /api/retract with `{ packageHash, retractionToken }`

## Threat Model

**What is NEVER stored:**
- Original files (images, videos, audio, documents)
- Raw filenames (only SHA-256 of filename is stored)
- GPS coordinates or exact locations
- Street addresses
- Victim/witness/suspect names
- Phone numbers
- Vehicle plates
- IP addresses (only a truncated hash for rate limiting, never associated with records)
- Public notes (private notes stay local in the proof package only)
- Any personally identifying information

**What IS stored (only if user explicitly submits):**
- SHA-256 fingerprint (package hash)
- Original file hash (optional, single-file records)
- Event type (kidnapping, detention, etc.)
- Evidence type (video, image, etc.)
- Country / region / city (broad location, user-provided)
- Safe descriptor metadata (file size bucket, duration bucket, GPS presence flag — not coordinates)
- `createdAtLocal` (browser clock, unverified, displayed with warning)
- `serverReceivedAtUtc` (server-recorded registry timestamp — proves the registry received the fingerprint by this server time)
- Quality level (A/B/C)
- Publication status
- Retraction token hash (not the raw token)

## Safe Descriptor Fields

Only fields that can be extracted with confidence are stored. Uncertain fields are omitted entirely.

Allowed:
- `mediaType`, `fileSizeBucket`, `durationBucket`, `resolutionBucket`, `aspectRatioBucket`
- `textWordCount`, `language` (rough: Arabic/English/mixed/unknown)
- `gpsMetadataDetected`: stored only as `"yes"` if GPS tags clearly detected; otherwise omitted entirely
- `exifMetadataDetected`: stored only as `"yes"` if EXIF metadata clearly detected; otherwise omitted entirely

Never stored:
- Codec, frame rate, exact capture time, exact GPS, device model, manufacturer, serial number

## API Endpoints

- `GET /api/healthz` — health check
- `GET /api/records` — list public records (`accepted_public`, `exact_match_published` only)
- `POST /api/records` — submit fingerprint (auto policy check; Quality D rejected; 100 kb limit)
- `GET /api/records/stats` — aggregate stats (public records only)
- `GET /api/records/:packageHash` — fetch public record by hash (404 for non-public)
- `POST /api/retract` — retract a record using packageHash + retractionToken

## Database Tables

- `witness_records` — public fingerprint records with publication_status and retraction token hash

## Environment Variables / Secrets

- `DATABASE_URL` — PostgreSQL connection string (runtime-managed)
- `SESSION_SECRET` — session signing secret


## Safety & Spam Controls

- Honeypot field on submission form (blocks simple bots)
- Rate limiting: 10 submissions per IP per hour (in-memory)
- Server-side location field validation: rejects phone numbers, GPS coords, URLs, email addresses, street addresses, vehicle plates, violent language
- Duplicate hash detection: returns `already_registered` with link to existing record (409)
- Quality D records rejected with 400
- JSON body capped at 100 kb

## No Manual Review in v0.1

There is no admin dashboard or manual approval step. Records are either:
- Accepted immediately (`accepted_public`) if they pass all policy checks
- Rejected with a reason (`rejected_by_policy` — HTTP 400) if they fail

## No Telegram in v0.1

Telegram share button has been removed. Available actions are:
- Download proof package (includes retraction token)
- Copy public record
- Submit to registry
